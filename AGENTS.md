# AGENTS.md — RuDub Studio (форк Audacity 4.0.0)

Этот файл — единая инструкция для любого ИИ-агента в этом репозитории
(Claude Code, Codex, Cursor и др.). Один файл — одна правда.
Не дублировать эти правила в других местах.

## 1. Что это за проект

Форк audacity/audacity, тег Audacity-4.0.0, рабочая копия d:/auda/audacity.
Дорабатывается под полный дубляж игры (EN -> RU) одним человеком:
импорт метаданных реплик, запись, редактирование, AI-очистка голоса,
LLM-адаптация текста, голосовой сервис, пакетная обработка, экспорт.
Целевая платформа — только Windows. Только online-режим внешних сервисов.
Масштаб одного проекта: десятки тысяч реплик, тысячи сцен, десятки
файлов игры.

Архитектура Audacity 4 (подтверждено Шагом 1):
- Слой 1 — src/ : новые модули Au4 (Qt 6 QML, view-модели, сценарии).
- Слой 2 — muse framework : модульность, IOC, actions, shortcuts,
  dockwindow, workspace, network.
- Слой 3 — au3/libraries : ядро аудио из Audacity 3 без wx-GUI,
  доступ из Au4 через src/au3wrap (DomAccessor, IAu3Project).
- au3/src (легаси wx-приложение, включая BatchCommands/Macros)
  и au3-menus (CommandManager) НЕ собираются в AU4. Не ссылаться
  на них как на доступный функционал.

## 3. Границы задачи (обязательно соблюдать)

- Приложение НЕ занимается конвертацией .wem ни в одну сторону.
- Вход — готовые WAV, сконвертированные вручную до импорта.
- Результат работы приложения — WAV/lossless. Обратную конвертацию
  в .wem я делаю вручную сам.
- Не добавлять зависимости от vgmstream, Wwise CLI, sound2wem
  в основной функционал. Будущий WEM-модуль — только раздел
  "отложено" в roadmap, без реализации.
- Только Windows. Не усложнять ради кроссплатформенности.
- Фолбэки offline для внешних сервисов не проектировать.
- Референсные WAV хранятся ВНУТРИ .aup3 по умолчанию (требование
  "один файл — другой ПК"). Режим внешних ссылок — только как опция,
  если оценка размера на Шаге 2 покажет неприемлемый размер.
- Все пути к файлам/классам указывать дословно из рабочей копии тега
  Audacity-4.0.0, без пересказа по памяти. Точный путь фреймворка
  (muse/framework vs muse_framework) уточнить по рабочей копии.

## 4. Зафиксированные решения (ответы на вопросы Шага 1)

1. WAV-паттерн по умолчанию: {guid}.wav, регистр нечувствителен,
   вложенные подпапки сканируются рекурсивно. Не хардкодить —
   вынести в настройку импортёра. Точный паттерн дампа подтверждается
   файлом docs/requirements/sample.json и реальной папкой.
2. JSON: один большой или по одному на file_id — принимается оба
   варианта. Кодировка UTF-8. Структура
   {file_id: {quest_id: {guid: {en, ru, speaker_name,
   speaker_internal, dur}}}}. Поле dur — секунды (float).
   Порядок ключей JSON = порядок реплик, сохранять как есть.
3. Циклическая запись: строго "каждый повтор — отдельная
   дорожка-тейк", старые не удаляются автоматически. Штатный
   punch/loop-тейкинг в одной дорожке не устраивает.
4. Голосовой сервис: конкретный API не фиксируется. Проектировать
   как настраиваемый провайдер (endpoint + auth + модель в настройках).
   Лимит — символы/кредиты, уточняется при реализации 6.11.
5. LLM-провайдер: приоритет — облачный OpenAI-совместимый API
   с переключением без пересборки. Второй провайдер того же
   интерфейса — Ollama-совместимый локальный.
6. AI-очистка: отдельный локальный Python-процесс (RNNoise /
   DeepFilterNet и подобные), вызывается из приложения, не блокирует
   запись. Два профиля: слабый (CPU / RTX 4060) и мощный (RTX 4080S).
7. Хранение референсов: см. раздел 3 — внутри .aup3 по умолчанию.
8. Qt: сборка по BUILDING.md (Qt 6.10 MSVC 2022 x64, CMake >= 3.24,
   Ninja). Процедуру сборки под мою машину зафиксировать в roadmap.

## 5. Стиль и соглашения кода

- Новый код — C++20 (подтверждено: CMAKE_CXX_STANDARD 20 в корне).
  Указания про C++17 в старых черновиках считать недействительными.
- Следовать существующему стилю Audacity в затронутых модулях.
  Qt-идиомы — соответствующие обнаруженной версии Qt.
- Весь пользовательский текст интерфейса — только на русском языке.
- Любые изменения состояния проекта — только через существующий
  механизм IProjectHistory / pushHistoryState / startUserInteraction /
  endUserInteraction. Параллельный механизм отмены запрещён.
  Для каждого модуля в roadmap указать точный механизм отмены.
- Регистрация нового модуля приложения — через appfactory.cpp
  (app->addModule). Новая панель — DockPanel в ProjectPage.qml +
  QML-файл + C++ view-модель.
- Коммиты — conventional commits, описание на русском языке.
- Один PR = один модуль из roadmap.

## 6. Функциональные требования

### 6.1 Новый тип проекта "Дубляж"
Выбор типа (обычный/дубляж) при создании. Тип "дубляж" хранит в одном
файле .aup3 через ProjectFileIOExtension: аудио (референсы, тейки,
мастер), метаданные реплик, историю текстов, журнал заданий, маппинг
персонаж->голос. Открывается на другом ПК без дополнительных папок.

### 6.2 Модель данных и импорт
Иерархия: файл игры -> сцена -> реплика. Импорт JSON (см. раздел 4 п.2).
Пустой speaker_name -> "UNKNOWN". Сопоставление WAV по guid из отдельно
указанной папки (см. раздел 4 п.1). Нет файла -> статус "нет референса",
не блокирует остальных. Сверка фактической длительности WAV с dur —
расхождение предупреждение. Повторный/инкрементальный импорт без потери
сделанной работы. Строительный блок аудио — Au3Importer::importIntoTrack.
Массовый импорт с прогрессом/логом/фоном — писать свой сервис поверх.

### 6.3 Панель списка реплик
Дерево/таблица файл -> сцена -> реплики, виртуализация, без лагов
на десятках тысяч строк. Колонки: статус, спикер, EN, RU, длительность
референса, расхождение длительности. Фильтры: UNKNOWN, статус,
расхождение, отсутствующий референс. Полнотекстовый поиск. Двойной
клик — открывает референс и текст в рабочей зоне.

### 6.4 Запись и треки
ASIO (Focusrite), 1 моно-канал. PortAudio + ASIO SDK уже в muse_deps,
PA_USE_ASIO=ON. Референсная дорожка — locked (только mute/solo),
в Au4 такого флага нет — проектировать свой. Отдельная именованная
дорожка "мастер". Циклическая запись — см. раздел 4 п.3. Мониторинг
входа по умолчанию выключен, включаемый программно. Настраиваемая
частота дискретизации проекта.

### 6.5 Автооценка тейков
Индикатор годности в реальном времени (громкость, клиппинг, совпадение
длительности) — подсказка, не вердикт. Метрики снимать с записанного
клипа (au3-wave-track-fft, meter, FindClippingBase). Ручная маркировка
и компоновка лучшего тейка в мастер.

### 6.6 Редактирование
Штатное покрытие проверить: обрезка, разделение, перемещение, фейды,
кроссфейд, громкость, нормализация, тишина, реверс, тайм-стрейч без
тона (SBSMS/SoundTouch, Clip.speed/stretchToMatchTempo). Добавить
как операции trackedit через IProjectHistory: "Подогнать под референс"
(стретч под длительность), "Выровнять по референсу" (привязка начала),
"Отправить в мастер" (перенос + автокроссфейд).

### 6.7 Надёжность
Undo/redo на всю сессию, сохраняется в .aup3 (IProjectHistory + au3
UndoStack). Автосейв уже включён по умолчанию 5 мин, только при
изменениях (ProjectAutoSaver) — проверить и оставить. Восстановление
после сбоя через isRecovered/autosave — добавить предложение
со временем снимка при старте, если отсутствует.

### 6.8 Экспорт результата
Экспорт мастер-дорожки в WAV/lossless, имя файла = guid реплики.
Пакетный экспорт по фильтру (файл/сцена/спикер/статус) со структурой
имён из метаданных. Строительный блок — IExporter::exportData.
WEM — только раздел "отложено", не реализовывать (см. раздел 3).

### 6.9 Адаптация текста (LLM)
Панель: EN, текущий RU, 3 варианта адаптации с объяснением. Для каждого
— слоги, оценка попадания в длительность, совпадение первого/последнего
звука. Провайдеры — см. раздел 4 п.5, настройка без пересборки.
История версий с откатом. Модуль целиком с нуля (muse network + QML).

### 6.10 Очистка голоса (AI)
Офлайн-цепочка: шумоподавление, гул, свистящие/взрывные — каждый шаг
включаемый, прослушивание "было/стало". Внешний Python-процесс,
см. раздел 4 п.6. Пакетный прогон по фильтру с логом и перезапуском
только ошибок. Штатные Noise Reduction / Click Removal можно вызывать
программно как часть цепочки.

### 6.11 Голосовой сервис
Режимы "голос-в-голос" и "текст-в-голос". Провайдер настраиваемый
(см. раздел 4 п.4). Привязка персонажа (speaker_internal) к голосу,
вариации (шёпот) как отдельные настройки. Кэш — повтор не тратит лимит.
Индикатор остатка, блокировка при нуле. Предрасчёт расхода перед batch.
Модуль целиком с нуля.

### 6.12 Пакетная обработка
Движок заданий: область (проект/файл/сцена/спикер/выделенные) + цепочка
(очистка -> голосовой сервис -> подгонка -> экспорт). Очередь переживает
перезапуск (хранение через 6.1), прогресс/лог, перезапуск только упавших.
Пишется с нуля (Macros в AU4 нет).

### 6.13 Интерфейс
Полностью русский. Тёмная тема по умолчанию (muse draw, темы в комплекте).
Хоткеи переназначаемые через framework/shortcuts, экспорт/импорт раскладки
(действия — через actions/UiActionList). Панели перетаскиваемые,
раскладка запоминается (workspace + Muse.Dock).

## 7. Формат результата шагов АРХИТЕКТУРА + ПЛАН ПО МОДУЛЯМ

1. Актуальная схема регистрации эффектов на теге Audacity-4.0.0
   (ядро + регистрация + QML) дословно по коду тега — с учётом
   ревампа audio plugins лета 2026. Минимальный живой пример
   (fade/amplify или их актуальный аналог).
2. Дословные доказательства: что au3/src (BatchCommands/Macros)
   не входит в сборку AU4 и что au3-menus/CommandManager не собирается.
   Цитаты из CMakeLists.
3. docs/plans/roadmap.md — последовательность модулей (1 модуль =
   1 PR), для каждого: затрагиваемые файлы/классы, механизм отмены,
   оценка сложности/рисков, критерий готовности, что переиспользуется /
   что расширяется / что с нуля.
4. Размещение нового кода: один src/dubbing/ или несколько модулей —
   с обоснованием по правилам Muse Framework и указанием точки
   регистрации DockPanel в ProjectPage.qml.
5. Оценка размера .aup3 при хранении референсов внутри
   (формула: число реплик x средняя длительность x битрейт) и порог,
   после которого нужна опция внешних ссылок.
6. Раздел "отложено" — будущий WEM-модуль без реализации.
7. Явные вопросы мне там, где данных не хватает.

## Формат отчёта о расхождениях с согласованным планом

Если реализация отклоняется от architecture.md/roadmap.md, раздел
"Расхождения" в отчёте обязан разделять два типа изменений:

1. "Техническая деталь реализации" — не влияет на видимое поведение
   пользователя и согласованные UX-контракты (пример: сортировка ключей
   QJsonObject, внутренний способ поиска клипа).
2. "Изменение контракта" — меняет то, что видит/делает пользователь
   или что было явно зафиксировано как решение (пример: количество
   нажатий Ctrl+Z для отмены операции, формат хранения данных).

Пункты категории 2 не заносятся в общий список "уточнений" — по каждому
такому пункту отдельный явный вопрос пользователю с двумя вариантами
и рекомендацией, до продолжения работы над следующим модулем.
